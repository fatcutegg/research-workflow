# 実験設計

## 実行環境

共通の実行環境設定は **00-orchestrator（共通実行環境）** を参照すること。

## 目的

実験の計画をあなたと討論し、合意を記録した上で実験ディレクトリを作成します。1 回の討論で複数の実験を計画することも、実験結果を受けて再討論することも可能です。

## トリガー

- 「次の実験を考えたい」
- 「アプローチを変えたい」
- 「実験計画を立てたい」
- 「新しい手法を試したい」
- 「前回の結果を受けて再検討したい」

## 討論フェーズ

### Step 1: 実験目的の確認

```
agent: 「今回の実験の目的は何ですか？
   A: 新しい手法の検証
   B: パラメータ探索・調整
   C: ablation study（どの要素が効いているか）
   D: 比較実験（ベースライン vs 提案手法）
   E: 再現性確認・バグ修正後の再実行
   F: その他」

あなた：「A と C の両方をやりたい」
```

Direction Check:

- この実験の仮説は明確か
- 前回の結果とどう関係するか
- 検証可能な範囲か（リソース・時間的に）

### Step 2: 実験内容の詳細

```
agent: 「実験内容を具体化します。
   アプローチ:
     A: 既存モデルに attention 層を追加
     B: foot pressure の融合方法を変更
     C: データ拡張を導入

   データセット:
     A: 現在のもの（20名分）
     B: 新しいデータを追加（未収集）

   評価指標:
     - accuracy
     - F1-score（クラス不均衡対策）
     - 混合行列」
```

各項目はあなたと討論して決定します。各 Step 内に複数のタスクが存在する場合があります：

```
タスクA: attention 層の位置を決定する
タスクB: ハイパーパラメータの初期値を設定する
タスクC: 比較対象のベースラインを決める
```

タスクは英数字と記号のみでラベル付けします（タスクA, タスクB, task-1, task-2 等）。

### Step 3: 合意と記録

討論が完了したら、合意内容を DC（決定記録）として保存します。

```
決定内容を DC-{番号} に記録します：

```
# DC-{番号}: {実験名}

## EP-01-S: 目的（簡略）
{実験の目的}

## EP-02-S: 仮説（簡略）
{検証したい仮説}

## EP-03-S: 方法（簡略）
{アプローチ、モデル構造}

## EP-04-S: データセット（簡略）
{使用するデータ}

## EP-05-S: 評価指標（簡略）
{accuracy, F1 等}

## EP-06-S: 期待される結果（簡略）
{成功/失敗の基準}

## 実験リスト
- EXP-{番号}: {実験1}
- EXP-{番号}: {実験2}（オプション）

## 詳細
experiments/EXP-{番号}-{説明}/README.md 参照
```
```

### Step 4: 複数実験の計画

1 回の討論で複数の実験を計画できます。その場合、順序と依存関係を明確にします：

```
agent: 「2 つの実験を計画しました：
   EXP-004: attention 層追加（単独効果の確認）
   EXP-005: attention + foot pressure 融合（組み合わせ効果）
   
   EXP-005 は EXP-004 の結果次第で実行します。
   EXP-004 で効果が確認できなかった場合、
   EXP-005 は再設計します。よろしいですか？」
```

### Step 5: 再討論のルート

実験結果の Review や Post-Inspect で問題が発覚した場合、03 に戻って再討論します：

```
Review → 問題発覚
  例: attention が効いていない、コードにバグがあった
  → 03-experiment-design に戻る
  → 原因分析 → 新しい計画（EXP-{新番号}）
  → 合意 → 実行
```

## Pre-Inspect（実行前検証）

- 仮説は検証可能か
- 評価指標は目的に合っているか
- データセットは利用可能か
- 実験の順序と依存関係は明確か
- DC（決定記録）は正しく保存されたか
- 実験ディレクトリ名の番号は既存と重複していないか
- EXP counter と DC counter の現在値を確認する（state.yaml）

## Post-Inspect（実行後検証）

- DC の内容と実験計画書（README.md）に矛盾はないか
- 空 ipynb のセクション構成は適切か
- 次の実験に進む前に前回の結果を確認したか
- EXP counter と DC counter が実際のファイル数と一致するか確認する
- 不整合があれば実ファイル数を優先して state.yaml を修正する

## 出力

```
decisions/
└── DC-{番号}-{説明}.md

experiments/
└── EXP-{番号}-{説明}/
    ├── README.md          ← 実験計画書（EP セクション付き）
    └── experiment.ipynb   ← 空テンプレート
```

反映先:

```
research/state.yaml         ← EXP counter, DC counter 更新
```

### README.md テンプレート

```markdown
# EXP-{番号}: {実験名}

## EP-01-D: 目的（詳細）
{なぜこの実験をするか、何を検証するか}

## EP-02-D: 仮説（詳細）
{検証したい仮説}

## EP-03-D: 方法（詳細）
{アプローチ、モデル構造の概要}

## EP-04-D: データセット（詳細）
{使用するデータ}

## EP-05-D: 評価指標（詳細）
{accuracy, F1 等}

## EP-06-D: 期待される結果（詳細）
{どうなったら成功か、どうなったら失敗か}

## EP-07: 合意記録
DC-{番号} 参照
```

### experiment.ipynb テンプレート（空）

```ipynb
NB-01: 実験目的（説明文）
NB-02: 環境設定（import, seed fix, device）
NB-03: データ準備
NB-04: モデル定義
NB-05: 学習ループ
NB-06: 評価・可視化
NB-07: 結果保存
```

NB の各セクションは必要に応じて追加・省略可能です。各セクション内に複数の CB（コードブロック）を持たせることができます。

## 次のステップ

実験計画書の確認後、04-experiment-code に進むかどうかを相談する。

## HARD-GATE

- あなたとの討論なしに実験計画を確定してはならない
- DC（決定記録）の保存なしに実験ディレクトリを作成してはならない
- 実験の順序と依存関係を確認せずに複数実験を計画してはならない
- 前回の実験結果（Post-Inspect）の確認なしに次の実験に進んではならない
- 不確かな仮説を確かと表現してはならない
- Step 内の複数タスクはすべて討論で合意してから次に進む
